설치 ​

배포 프로파일·배포 형태 선택, 사전 점검, 설치 마법사, 설치 직후 확인, 포트.

1. 전제와 용어 ​

설치 전에 두 가지를 정합니다. 망 환경을 정하는 프로파일과 메타DB 위치를 정하는 배포 형태입니다. 두 항목은 서로 독립적으로 고릅니다.

1-1 배포 프로파일 — airgap / connected ​

제품은 단일 노드 온프레미스 배포를 기본으로 하며, **폐쇄망(에어갭)**에서도 별도 준비 없이 설치·운영할 수 있도록 구성합니다.

고객 네트워크에 인터넷 연결이 전혀 없어도 됩니다. 라이선스도 외부 활성화 서버에 접속하지 않고 오프라인 서명 파일(.lic)로 검증합니다.

참고 미설정·빈 값·오타는 모두 airgap 으로 처리합니다. 기존 폐쇄망 배포는 아무것도 설정하지 않아도 지금과 같이 동작합니다.

1-2 배포 형태 — 메타DB를 어디에 두는가 ​

망 환경과는 별개로 정하는 항목입니다. 메타DB(제품 자체 데이터)를 어디에 두고 노드를 몇 대 둘지 정합니다.

설치 마법사가 이 항목을 묻고 .env 의 GAEA_DB_BACKEND(HA 면 GAEA_HA 도)에 기록합니다.

표 1-2 배포 형태 3선택지

선택지내용노드 수
single (기본)내장 SQLite. 추가 질문 없음 — .env 가 바이트 동일 유지1

주의 망 환경과 배포 형태는 따로 고릅니다. 폐쇄망에서도 PostgreSQL 을 쓸 수 있고, 인터넷망에서도 내장 SQLite 를 쓸 수 있습니다.

참고 이미 내장 SQLite 로 운영 중인 설치를 PostgreSQL 로 옮길 때는 재설치가 아니라 이관입니다. 마법사에서 배포 형태만 바꿔 다시 설치하면 빈 메타DB 로 뜨고 기존 데이터는 따라오지 않습니다. 서버를 내린 상태에서 서버 이미지 안의 이관 도구(./gaea.sh pg-migrate)로 옮깁니다. 절차는 「업그레이드 › 2-2 PG 백엔드 분기」에 있습니다.

PostgreSQL 을 쓴다고 HA 가 되지 않습니다 ​

single-pg 는 여전히 단일 노드입니다.

HA 는 GAEA_DB_BACKEND=postgres + GAEA_HA=on + 라이선스 multi-node-ha 자격, 셋 다 참일 때만 켜집니다.

하나라도 빠지면 그 노드는 경고 1줄과 함께 단일 노드로 정상 기동합니다. 부팅 실패가 아닙니다.

1-3 번들 PostgreSQL 이미지 ​

기본 번들에는 들어 있지 않습니다. SQLite 로 쓰는 대다수 설치의 매체 용량을 늘리지 않으려는 결정입니다.

폐쇄망에서 번들 PG(single-pg·bundled)를 쓰려면 postgres:16 이미지가 필요합니다. 반입 경로는 둘입니다.

1-5 사전요건과 사전 점검 ​

번들과 서버 CPU 맞추기 ​

번들 안 이미지는 빌드한 CPU 아키텍처에서만 동작합니다(일부 모듈이 아키텍처별로 미리 컴파일되어 있습니다). 아키텍처가 맞지 않는 번들은 반입한 뒤에야 실패하므로, 번들을 풀자마자 두 값을 대조합니다.

sh
cat system/PLATFORM   # 번들 스탬프 — linux/amd64 또는 linux/arm64
uname -m              # 이 서버 — x86_64 이면 linux/amd64, aarch64 이면 linux/arm64
  • install-offline.sh 의 A7 검사가 system/PLATFORM 과 이 서버(docker version 의 Server.Os/Arch)를 대조해, 다르면 docker load 전에 중단합니다(우회 --ignore-platform-check — 돌지 않는 번들을 알고 쓸 때만).
  • 맞는 번들이 없으면 벤더가 대상에 맞춰 다시 만듭니다 — ./pack-offline.sh --platform linux/amd64\|linux/arm64 --app <react\|vue>. 빌드 호스트가 amd64 가 아니면 --platform 을 생략할 수 없습니다.

참고 벤더가 Apple 실리콘 Mac(arm64) 위에서 시험 설치를 하려면 linux/arm64 번들이 필요합니다. 고객에게 나가는 linux/amd64 번들은 그 Mac 에서 설치 검사(A7)를 통과하지 못합니다.

2. 설치 ​

신규 설치는 두 경로가 있습니다. 웹 설치 마법사(권장)와 터미널 마법사입니다. 두 경로 모두 값을 모아 .env 를 만든 뒤, 실제 설치 로직은 system/install-offline.sh 하나에 위임합니다. 번들을 풀면 루트에는 운영자가 쓰는 것(README.txt · setup.sh · gaea.sh · demo.sh · upgrade.sh · manuals/ · file-sources/)만 있고 나머지 구성은 system/ 에 있습니다(「설치 › 2-7 설치 직후 확인」 폴더 안내).

2-1 웹 설치 마법사 ​

번들에 든 서버 이미지로 임시 컨테이너를 띄워 설치 화면을 제공합니다. 추가로 반입할 것은 없습니다.

컨테이너에는 docker 소켓을 연결하지 않습니다. 설치는 호스트의 setup.sh 가 실행하고, 웹 화면은 입력값 확인·파일 기록·설치 로그 전달만 맡습니다.

항목내용
노출 범위127.0.0.1:<포트>(기본 9310)에서만 열립니다. 평문 HTTP 를 네트워크에 여는 옵션은 제공하지 않습니다.
인증일회성 토큰. 시작 시 출력하는 http://127.0.0.1:9310/#t=<토큰> 링크로만 열립니다.
수명완료·중단·오류 어느 경로에서도 컨테이너와 .setup-web/ 을 정리합니다. 유휴 30분이면 스스로 종료합니다.

절차

  1. 반입 매체의 번들을 서버에 풀고 그 디렉터리로 이동합니다(터미널 마법사 「설치 › 2-2 터미널 마법사」 도 같은 시작점입니다). 번들 이름의 버전이 곧 설치될 버전입니다.

    sh
    sudo tar xzf /media/usb/gaea-onprem-1.2.0-offline.tar.gz -C /opt
cd /opt/gaea-onprem-1.2.0-offline
cat system/VERSION system/PROFILE system/PLATFORM   # 번들 스탬프 확인(버전 · airgap/connected · 아키텍처)

  2. 번들 디렉터리에서 마법사를 띄웁니다.

    sh
    ./setup.sh --web
./setup.sh --web --web-port 9310   # 포트 지정(기본 9310, 127.0.0.1 전용)

  3. 원격 서버라면 사무실 PC 에서 SSH 로컬 포워딩을 엽니다. 로컬 포트와 서버 포트를 같게 둡니다. 마법사는 보안상 요청 주소(Host 헤더)의 포트가 자기 포트와 같을 때만 응답하고, 다르면 이유를 적은 403 을 돌려줍니다.

    sh
    ssh -L 9310:127.0.0.1:9310 <계정>@<서버>
# → 사무실 PC 브라우저에서 http://127.0.0.1:9310

  4. 화면의 단계를 따라 배포 형태와 데이터 경로를 정하고 설치 시작을 누릅니다. 진행 로그가 화면에 중계됩니다. 새로고침(F5)해도 같은 탭이면 이어집니다.

노드 잠금(node_lock) 라이선스 ​

노드마다 machine-id 가 다릅니다. 벤더가 단일 node_lock 으로 발급했다면 한 노드만 통과하고 나머지는 node_mismatch 로 막힙니다.

HA 배포는 벤더에 노드 수만큼 머신 ID 를 등록한 node_locks(목록) 발급을 요청합니다. 각 노드의 값은 제품 라이선스 페이지(/admin/license)의 「이 서버의 머신 ID」에서 복사합니다.

노드마다 머신 ID 와 MAC 주소를 함께 등록할 수 있습니다(노드 잠금 v1.5). 노드별로 종류를 골라 섞어 등록하거나, 한 호스트에 둘 다 일치해야 통과하도록(검증 방식 「모두 일치」) 요청할 수 있습니다 — 머신 ID 를 읽을 수 없는 환경(비-systemd)이나 더 강한 고정이 필요한 계약에 씁니다. MAC 값은 제품 라이선스 페이지의 「이 서버의 MAC 해시」에서 복사하며, 컨테이너 배포는 GAEA_NODE_MAC 주입 규약을 먼저 맞춥니다.

주의 노드 잠금 라이선스는 2026-09-12 이후 빌드에서만 요청하십시오. 그 이전 출하본(2026-09-04 판 — 단일 node_lock 을 머신 ID 해시와만 비교)에 MAC 잠금이나 다중 노드(HA) 라이선스를 발급하면, 정당한 호스트인데도 node_mismatch 로 막혀 제품이 Standard·무료 등급으로 내려갑니다. 라이선스에 함께 실리는 구버전 호환 필드로도 이 차단을 피할 수 없습니다. 벤더에 노드 잠금 라이선스를 요청하기 전에 제품을 먼저 업그레이드하세요.

sh
./gaea.sh keys export                 # → ./gaea-recovery-keys-<호스트>-<시각>.txt (권한 600)
./gaea.sh keys export --encrypt       # 12자 이상 암호로 잠근 .enc — USB 로 옮길 때 권장

설치 직후 할 일

  1. 파일을 서버 밖(USB·금고·사내 비밀 보관소)으로 옮깁니다. 백업 매체와 다른 곳 2곳 이상이 좋습니다.
  2. 서버에서는 지웁니다 — shred -u <파일>(없으면 rm).
  3. 암호화했다면 여는 법: openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -md sha256 -a -in <파일>.enc
항목내용

화면 출력키 이름과 지문(SHA-256 앞 16자)만. 다중 노드의 [ha] 키 지문, 백업 .enc 헤더의 키 지문과 같은 규칙이라 값 없이 대조할 수 있습니다
막히면「.env 에 보관할 키가 하나도 없습니다」= 설치가 끝나지 않은 디렉터리. --encrypt 를 비대화형으로 쓰려면 GAEA_KEYS_PASSPHRASE. 같은 이름 파일은 덮어쓰지 않습니다(--out)

2-9 Tibero 고객 — JDBC 확장 이미지 ​

Tibero 는 JDBC 로 연결해 서버 안에 JVM 이 필요합니다. 기본 이미지에는 없으므로 Tibero 를 쓰는 고객만 JDBC 확장 이미지(gaea-onprem-server-jdbc, OpenJDK 17)가 든 번들을 받습니다. 다른 고객의 설치 절차는 이 절과 무관합니다.

① 드라이버 jar 는 고객이 준비합니다 ​

Tibero JDBC jar(tibero6-jdbc.jar 등)는 티맥스소프트 소유 소프트웨어라 번들 어디에도 들어 있지 않습니다. 보유한 정식 jar 를 제품 설치 미디어 또는 Tibero 서버의 $TB_HOME/client/lib/jar 에서 얻되, Tibero 서버 버전과 맞는 것을 씁니다.

항목내용
방법 A — 볼륨 마운트(권장)설치 때 번들의 jdbc-drivers/ 에 jar 를 넣기만 합니다. 번들을 다시 만들 필요가 없고 jar 가 이미지에 남지 않으며, 드라이버 교체도 같은 폴더의 파일만 바꾸면 됩니다. 다른 폴더를 쓰려면 .env 의 GAEA_JDBC_DRIVER_DIR. 컨테이너 안 /opt/gaea/jdbc 에 읽기전용으로 올라갑니다
방법 B — 이미지에 동봉서버에 드라이버 파일을 둘 수 없는 환경용. 벤더가 빌드 머신의 deploy/onprem/jdbc-drivers/ 에 jar 를 넣고 번들을 다시 만들어야 합니다. 이 경우 docker-compose.jdbc.yml 의 드라이버 볼륨 한 줄을 주석 처리해야 마운트가 이미지 안 경로를 가리지 않습니다
jar 경로 지정어느 방법이든 .env 의 TIBERO_JDBC_JAR 에 컨테이너 안 절대경로를 반입한 파일명에 맞춰 적습니다. 기본 /opt/gaea/jdbc/tibero6-jdbc.jar

② 번들은 --with-jdbc 로 만듭니다(벤더) ​

벤더가 pack-offline.sh --with-jdbc 로 만든 번들만 확장 이미지와 docker-compose.jdbc.yml·jdbc-drivers/ 를 담고 있습니다. 번들 안에 이 파일들이 있는지로 확장 번들임을 알 수 있습니다.

③ 설치 ​

sh
tar xzf gaea-onprem-<VERSION>-offline.tar.gz && cd gaea-onprem-<VERSION>-offline
cp <고객 드라이버>/tibero6-jdbc.jar ./jdbc-drivers/    # 방법 A — jdbc-drivers/ 는 번들 루트
./setup.sh                                             # 8단계에서 JDBC·jar 이름을 묻습니다
# 또는 cp system/.env.example .env → TIBERO_JDBC_JAR 을 맞춘 뒤 ./system/install-offline.sh

install-offline.sh 는 번들에 오버레이 파일이 있으면 자동으로 인식합니다(별도 인자 없음). 설치 마법사를 쓰면 8단계에서 JDBC 를 묻습니다(비대화형은 SETUP_JDBC·SETUP_JDBC_JAR).

④ 동작 확인 ​

sh
./gaea.sh compose ps                                   # server 가 healthy
./gaea.sh compose exec server java -version            # OpenJDK 17 출력
./gaea.sh compose exec server ls -l /opt/gaea/jdbc     # 반입한 tibero*.jar 가 보이는지

마지막으로 관리 화면에서 Tibero 데이터소스를 만들어 연결 테스트까지 성공해야 끝입니다. 흔한 실패는 아래와 같습니다.

표 2-8 Tibero 연결 실패와 조치

증상원인·조치
「Tibero JDBC 설정이 없어요: 환경변수 TIBERO_JDBC_JAR 에 … jar 경로를 지정하세요」.env 에 값이 없거나 컨테이너 안 경로가 아닙니다. ./gaea.sh compose exec server ls /opt/gaea/jdbc 로 실제 경로를 확인해 고친 뒤 재기동

주의 업그레이드: 기존 설치가 확장본이면 새 번들도 반드시 --with-jdbc 로 만든 것이어야 합니다. 그렇지 않으면 업그레이드가 실패해 되돌릴 때 이전 확장 이미지를 찾지 못합니다. 또 Tibero 고유 SQL 문법과 실제 서버 연결은 벤더 환경에서 검증할 수 없으므로, 위 연결 테스트로 현장에서 확인한 뒤 운영에 투입합니다.

2-11 지도 배경(베이스맵) ​

지도 시각화의 배경 지도는 설치기가 망 환경에 맞춰 정합니다. 설치기는 .env 의 비어 있는 키만 채우고, 운영자가 넣은 값은 그대로 둡니다. 설치 뒤에는 관리자 콘솔(/admin) 「시스템 관리자」 탭의 「지도 배경」 카드에서 저장한 설정이 이 값보다 우선합니다.

표 2-10 지도 배경 기본값(설치기가 채우는 값)

키값
GAEA_MAP_BASEMAP폐쇄망 + 타일 동봉 번들 = bundled · 폐쇄망 + 타일 없음 = none(행정경계만 그립니다) · 인터넷망 = osm(OpenStreetMap 공식 타일). 폐쇄망에서는 인터넷 소스(osm · vworld)를 고를 수 없고(서버가 거부), 사내 https 타일 서버(xyz · style)는 쓸 수 있습니다
GAEA_MAP_TILES_DIR타일을 푸는 호스트 경로. 기본 ./map-tiles(번들 루트 기준). 이미 같은 sha256 의 타일이 있으면 다시 풀지 않습니다. 다른 디스크에 두려면 절대경로로 바꿉니다
GAEA_MAP_TILE_URL · GAEA_MAP_STYLE_URL인터넷망에서 쓸 타일 주소({z}/{x}/{y}) · 스타일 JSON 주소. 비우면 소스별 기본값
GAEA_MAP_CSP_HOSTS브라우저가 외부·사내 타일 서버에서 타일을 받을 수 있게 웹 서버(edge) 보안 정책(CSP)에 더하는 주소(쉼표 구분, 공백 없이). 설치기가 위 주소와 실행 중 서버의 지도 설정(관리자 화면에 저장된 값)에서 찾아 더합니다(빼지는 않습니다)

주의 관리자 화면에서 인터넷 지도 주소를 바꾸면 화면에 「설정 다시 적용 필요」가 뜹니다. 이때 ./setup.sh 를 한 번 더 실행해야 새 주소가 CSP 에 들어가 지도가 뜹니다(기존 값은 그대로 기본값으로 나옵니다). 스타일 JSON 이 다른 주소(글꼴·스프라이트·타일)를 부르면 그 주소를 GAEA_MAP_CSP_HOSTS 에 직접 더한 뒤 ./gaea.sh restart 합니다.

참고 지도 주소는 로그인하지 않은 사용자의 브라우저에도 그대로 전달됩니다. 그래서 주소에 아이디·비밀번호(user:pass@)나 access_token·key 같은 인증 값을 넣으면 서버가 저장을 거부합니다(VWorld 인증키는 GAEA_MAP_VWORLD_KEY 로 따로 넣고, 서버가 타일 주소에 끼워 넣습니다). 카드에도 「이 주소는 로그인하지 않은 사용자에게도 그대로 전달돼요.」 안내가 있습니다.

번들 타일은 OpenStreetMap 데이터(ODbL 1.0)로 만든 것입니다. map-tiles/ATTRIBUTION.txt 를 지우지 마십시오. 지도 화면은 출처 표기(© OpenStreetMap contributors)를 자동으로 붙입니다. 타일은 데이터가 아니라 설치 자산이라 백업 대상이 아니며, 같은 번들에서 다시 풀 수 있습니다.

./setup.sh --non-interactive 는 질문 대신 아래 환경변수를 읽습니다(CI·무인 설치). SETUP_BASE_URL 만 무조건 필수이고, 나머지는 고른 선택지에 따라 필수가 됩니다. 빠진 필수값은 「비대화형 모드인데 필수값 … 비어 있습니다」로 설치 전에 중단합니다. 같은 목록을 서버에서 ./setup.sh --help 로 볼 수 있습니다.

SETUP_BASE_URL=https://gaea.corp.local SETUP_ADMIN_EMAIL=admin@corp.local \

C 비도커(systemd) 대안의 주의점 ​

컨테이너를 쓸 수 없는 환경을 위한 대안(systemd 유닛 gaea-server.service)이며 권장 경로가 아닙니다. 절차서와 유닛 파일은 기술지원 창구에 요청합니다.

항목내용
GAEA_BIND_HOST=127.0.0.1nginx 가 같은 호스트에 있을 때 반드시 둡니다 — 없으면 API 가 0.0.0.0:5180 에 바인드해 nginx 를 건너뛴 직접 접근이 열립니다
GAEA_TRUST_PROXYuniquelocal 이 아니라 앞단 nginx 의 정확한 주소(같은 호스트면 loopback). nginx 는 proxy_set_header X-Forwarded-For $remote_addr; 로 덮어씁니다(이어 붙이면 위조된 X-Forwarded-For 값이 남습니다)
NODE_ENV=production유닛 파일이 Environment=NODE_ENV=production 을 EnvironmentFile 앞에 고정합니다. 서버도 NODE_ENV 가 비어 있으면 로컬 모드로 보지 않습니다
