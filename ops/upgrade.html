업그레이드 ​

오프라인·연결 환경 업그레이드 9단계, PostgreSQL 백엔드, 다중 노드 순서, 웹 콘솔 업그레이드.

2. 업그레이드 ​

DB 마이그레이션은 앞으로만 적용되며(forward-only), 되돌리는 마이그레이션은 없습니다. 9단계 중 ⑤ 백업이 사실상 유일한 롤백 수단이므로 건너뛰지 않습니다.

2-1 offline / connected 9단계 ​

업그레이드는 새 번들 루트의 ./upgrade.sh 로 시작합니다. 번들 프로파일에 따라 폐쇄망은 system/upgrade-offline.sh, 인터넷망(레지스트리 pull)은 system/upgrade-connected.sh 를 호출하고, 나머지 옵션은 그대로 넘깁니다.

두 스크립트는 ③ 이미지 반입 단계만 다릅니다. 나머지 8단계는 반입 경로와 관계없는 데이터 보호 절차라 같습니다.

실행 절차 — 스크립트를 부르기 전에

  1. 새 번들을 새 디렉터리에 풉니다(기존 설치 디렉터리에 덮어쓰지 않습니다). 예: /opt/gaea-onprem-1.2.1-offline. 번들에 동봉된 CHANGELOG.md 로 무엇이 바뀌는지 먼저 확인합니다.
  2. 새 번들 루트에서 ./upgrade.sh --from <이전 설치 폴더> 를 실행합니다. --from 이 이전 설치의 .env(권한 600) · certs/ · file-sources/ · jdbc-drivers/*.jar 를 가져옵니다 — .env·certs/ 가 업그레이드가 승계하는 핵심입니다. 이전 설치가 1.2.x 이하의 평면 배치여도 같습니다(어느 배치든 둘은 루트에 있습니다). 이 폴더에 다른 .env 가 이미 있으면 덮어쓰지 않고 멈추고, .env 가 없으면 「.env 가 없습니다 — 이전 설치의 설정을 가져와야 합니다」 + → 조치: ./upgrade.sh --from … 로 정지 이전에 멈춥니다(안전).
  3. compose 프로젝트명(gaea-onprem)과 데이터 볼륨(gaea-data)이 고정이라 어느 디렉터리에서 실행하든 같은 실행 인스턴스를 제어합니다. 새 번들을 이전 폴더 위에 그대로 풀었다면 루트의 옛 구성 파일을 system/legacy-flat-<시각>/ 으로 옮깁니다(삭제 없음).
  4. 성공 메시지(「완료: 업그레이드 성공」)를 확인한 뒤부터는 새 디렉터리가 운영 디렉터리입니다 — 이후 ./gaea.sh 도 여기서 실행합니다.
  5. 지도 타일 — ② 검증 직후(서버 정지 전) 새 번들의 system/map-tiles.tar 를 GAEA_MAP_TILES_DIR(기본 ./map-tiles)에 풉니다. 이미 같은 sha256 의 타일이 있으면 건너뜁니다. 새 번들에 타일이 없고 GAEA_MAP_TILES_DIR 가 상대경로면 --from 이 이전 설치의 map-tiles/ 를 가져옵니다. 지도 이전 판에서 올라오면 비어 있는 GAEA_MAP_BASEMAP·GAEA_MAP_TILES_DIR(인터넷망은 GAEA_MAP_CSP_HOSTS 도)를 채웁니다. 타일은 설치 자산이라 정지 백업·자동 복원 대상이 아닙니다.
sh
tar xzf /media/usb/gaea-onprem-1.3.0-offline.tar.gz -C /opt
cd /opt/gaea-onprem-1.3.0-offline
./upgrade.sh --from /opt/gaea-onprem-1.2.0-offline     # .env·certs/·file-sources/ 를 가져와 업그레이드

실패 시 자동 복원의 결말 ​

표 2-2 ⑨ 자동 복원 결과

결말내용
복원 완료백업을 복원하고 이전 이미지·이전 GAEA_VERSION 으로 되돌린 뒤 ready 재확인을 통과한 경우입니다
복원 실패 → 정지(exit 2)백업 복원이 실패하면 구 이미지를 띄우지 않고 서비스를 정지 상태로 둔 채 백업 아카이브 경로와 아래 A/B 복구 절차를 출력합니다. .env 의 GAEA_VERSION 은 새 버전 그대로이므로, 손으로 ./gaea.sh start 해도 구 이미지가 새 스키마 위에서 기동하지 않습니다
이중 실패복원 후 ready 확인까지 실패한 경우입니다. 직접 조치가 필요하며, 「일상 운영 › 3-2 흔한 증상과 조치」 「복원 절차 실패」를 따릅니다
--skip-backup 으로 돌린 경우복원할 아카이브가 없으므로 이미지만 되돌립니다 — 안내 문구 「이미지만 복원 … DB 는 되돌리지 않았습니다」
sh
# A) 백업으로 되돌리기 — 복원 오류의 원인(키 불일치면 GAEA_BACKUP_ENC_KEY[_PREVIOUS])을 먼저 해소한다
./gaea.sh restore --dir upgrade-backups <스크립트가 출력한 아카이브 파일명>
#    .env 의 GAEA_VERSION 을 이전 버전으로 바꾼 뒤
./gaea.sh start
# B) 새 버전으로 전진 — ⑧ 실패 원인을 고친 뒤(./gaea.sh logs server)
./gaea.sh start
항목내용
모르는 마이그레이션 가드서버는 부팅할 때 DB 에 이 이미지가 모르는 마이그레이션이 적용돼 있으면 기동을 거부합니다(SQLite·PG 공통). 업그레이드를 되돌린 뒤 이미지와 DB 의 버전이 어긋난 채 기동하는 것을 막기 위해서입니다. 이를 알고도 띄워야 할 때만 GAEA_ALLOW_UNKNOWN_MIGRATIONS=1 을 씁니다(권장하지 않음 — 복구 직후 바로 제거)
Ctrl-C · kill(INT·TERM)④ 정지 이후에 받으면 진행 단계·정지 백업 경로·GAEA_VERSION·위 A/B 절차를 출력하고 exit 130 으로 끝납니다(자동 복원은 하지 않습니다)
터미널 끊김(HUP)무시하지 않고 출력을 번들 디렉터리의 upgrade-hangup-<시각>.log 로 돌린 채 계속 진행합니다. 장시간 작업이므로 tmux·screen 안에서, 또는 nohup ./upgrade.sh … > upgrade.log 2>&1 & 로 실행하기를 권합니다

경고 업그레이드가 확정되기 전에는 docker image prune 을 실행하지 않습니다. ⑨ 자동 복원은 이전 버전 이미지가 로컬에 남아 있어야 동작합니다. 이미지 정리는 새 버전이 /api/ready 200(strict 없이)으로 확정된 뒤에 합니다.

주의 업그레이드가 승계하는 것은 .env 와 certs/ 뿐입니다. docker-compose.yml 은 새 번들의 것으로 바뀌므로 그 파일에 직접 넣은 수정은 사라집니다. 그래서 운영자 설정은 전부 .env 에 둡니다 — 노드 잠금 라이선스도 마찬가지로 GAEA_NODE_MAC(MAC 잠금)과 GAEA_NODE_MACHINE_ID_FILE=/etc/machine-id(머신 ID 잠금) 두 키가 .env 에 있고 승계됩니다. 예전 안내대로 compose 의 /etc/machine-id 마운트 주석을 직접 풀어 둔 설치본이라면, 업그레이드 스크립트가 실행 중 컨테이너의 마운트를 보고 .env 에 GAEA_NODE_MACHINE_ID_FILE 을 대신 적어 줍니다(화면에 「.env 기록: GAEA_NODE_MACHINE_ID_FILE=…」 한 줄이 남습니다). 업그레이드 뒤 라이선스 페이지의 「이 서버의 머신 ID」가 null 이면 그 키가 .env 에 있는지 확인하십시오.

참고 같은 버전 번들(핫픽스 재빌드)도 받아들입니다. 이 경우 ③ 반입이 같은 태그를 새 이미지에 옮기므로, 스크립트는 반입 직전에 실행 중 이미지를 <이미지>:<버전>-prev 로 보존해 두고 ⑨ 롤백 때 그 이미지로 되돌립니다. 성공해도 -prev 태그는 남습니다(수동 롤백 재료 · 다음 업그레이드가 덮어씀 · 공간이 필요하면 docker rmi). 벤더 출하 규약은 「내용이 바뀌면 VERSION 의 patch 를 올린다」이며, 무엇이 바뀌었는지는 번들의 CHANGELOG.md 에 있습니다.

CLI 옵션 ​

표 2-3 upgrade-offline.sh · upgrade-connected.sh 공통 옵션

옵션의미
--force다운그레이드 강행. 스키마는 앞으로만 적용되므로 이미지를 되돌려도 DB는 되돌아가지 않습니다
--skip-backup⑤ 정지 백업 생략. 어드민 온라인 백업을 미리 받아 두었을 때만 씁니다
--backup-dir <dir>백업 저장 경로. 기본 upgrade-backups
--ready-timeout <초>준비 상태(ready) 확인 대기 상한(실제 경과 시간 기준). 기본 90초. 복원 후 재확인은 이 값과 관계없이 최소 60초
--yesPG 메타DB 배포의 정지 전 확인(yes 입력)을 생략합니다(비대화형). SQLite 배포에는 확인 단계가 없습니다
--allow-unsigned릴리스 서명(SHA256SUMS.sig)을 확인하지 못하거나 connected 이미지 다이제스트가 IMAGE-DIGESTS 와 달라도 경고 후 진행합니다. 출처를 다른 경로로 확인한 경우에만 씁니다. 운영 공개키는 2026-10-08 에 등록했으므로 그 뒤 번들은 서명이 없거나 맞지 않으면 이 옵션 없이는 정지 전에 멈춥니다. 그 전 빌드(공개키 미등록)의 스크립트만 「릴리스 서명 키 미등록」 경고를 내고 진행합니다

주의 --force 와 --skip-backup 을 함께 쓰면 「이 스크립트가 되돌릴 수단은 0 입니다」 경고 상자를 내고 실행합니다(막지는 않습니다). 다운그레이드를 강행할 때는 「정책: 스키마 다운그레이드는 지원하지 않습니다.」와 「스키마는 forward-only 입니다(down 마이그레이션 0종).」 안내를 화면에 출력합니다.

2-2 PG 백엔드 분기 ​

배포 형태가 single-pg(번들 PG)이거나 외부 PostgreSQL 이어도 같은 스크립트·같은 9단계로 업그레이드합니다. 달라지는 곳은 다섯 군데입니다.

PG 판으로 바뀌는 단계

  1. ③ 반입 뒤·정지 전 — 신규 이미지로 PG 사전 판정(migrate-check.js --pg: 접속 · _migrations 대장 · 이미지 마이그레이션 목록 대조와 다운그레이드 차단 · 스키마 소유 + DB CREATE · pg_dump 메이저 · 디스크)을 하고 yes 확인을 받습니다(비대화형은 --yes). 실패하거나 취소하면 서버를 정지하지 않습니다.
  2. ④ 번들 PG(meta-postgres)는 정지하지 않고 앱 서비스만 내립니다. 외부 PG 는 기동·정지 대상이 아닙니다.
  3. ⑤ 번들 이미지의 백업 CLI 로 pg_dump + DuckDB 를 한 아카이브로 뜬 뒤, 복원 CLI --dry-run --replace-schema 로 롤백에 쓸 수 있는지 바로 검증합니다. PG 에서는 --skip-backup 을 거부합니다.
  4. ⑥ 복사본 대신 운영 메타DB 에서 마이그레이션을 적용한 뒤 ROLLBACK 합니다(메타DB 무변경).
  5. ⑦~⑨ .env 의 GAEA_VERSION 을 기동 직전에 기록하고, ready 200 에 더해 응답 버전과 미적용 0 을 확인합니다. 실패하면 스키마 교체 복원 + 구 이미지·구 GAEA_VERSION 으로 자동 롤백합니다. 복원이 실패하면 구 이미지를 띄우지 않고 정지 + exit 2 입니다(2-1).
sh
migrate-check(pg): 사전 판정(읽기 전용)
  ✓ ① 접속: gaea@gaea_meta · 스키마 public · PostgreSQL 16.14
  ✓ ② 대장: _migrations 121행(데이터 마이그레이션 3행 포함)
  ✓ ③ 마이그레이션: 미적용 46건 — 119_audit_auth_key.sql … 164_pat_embed_theme.sql
  ✓ ④ 권한: gaea — 스키마 public 소유 · DB CREATE 가능(자동 롤백 성립)
  ✓ ⑤ 덤프 도구: pg_dump 16 = 서버 16

참고 외부 PG 계정에 스키마 소유권이 없으면 권한 판정(④)에서 업그레이드 시작 전에 멈춥니다. 자동 롤백에 필요한 스키마 교체를 할 수 없기 때문입니다. 이 경우 DBA 에게 권한을 받거나, 기술지원 창구에 PG 수동 업그레이드 절차(대안)를 요청합니다. 다중 노드 HA(GAEA_HA=on)는 이 스크립트로 업그레이드할 수 없으며, 정지 전에 중단합니다(아래 2-3).

SQLite 에서 PostgreSQL 로 옮기기 — 이관 ​

내장 SQLite 로 운영하던 설치를 PostgreSQL 메타DB 로 바꾸는 일은 업그레이드도 재설치도 아닌 이관입니다. 마법사에서 배포 형태만 바꿔 설치하면 빈 메타DB 로 뜨고 기존 데이터는 따라오지 않습니다. 이관은 서버를 내린 상태에서 한 번에 옮기며(무중단 이관은 없습니다), 서버 이미지 안의 도구(dist/scripts/migrate-sqlite-to-pg.js)를 ./gaea.sh pg-migrate 로 부릅니다.

이관 절차

  1. 정지 백업을 먼저 뜹니다(「백업 › 2-2 정지 백업 CLI」). 이관이 잘못되면 되돌릴 수단은 이 백업입니다.

    sh
    ./gaea.sh stop
./gaea.sh backup

  2. .env 에 PG 설정을 넣습니다 — GAEA_DB_BACKEND=postgres · GAEA_PG_URL(번들 PG 면 GAEA_META_PG_PASSWORD 도). 번들 PG 면 pg-migrate 가 meta-postgres 만 먼저 띄웁니다. .env 를 바꾸지 않고 하려면 --pg <URL> 로 대상을 직접 줍니다.

  3. 점검(아무것도 쓰지 않음) — 대상 접속, 대상 스키마가 비어 있는지, 원본이 정지 상태인지를 봅니다.

    sh
    ./gaea.sh pg-migrate --dry-run

  4. 실행 — 스키마 준비 → 표 적재 → 행 수·체크섬 검증 → 감사 체인 재검증 순으로 진행합니다. 보고서는 데이터 볼륨의 /data/migration-report.json 입니다.

    sh
    ./gaea.sh pg-migrate --yes

  5. 기동 후 GET /api/ready(strict 없이) 200 을 확인합니다.

    sh
    ./gaea.sh start

  6. 이관 직후 PG 백업을 새로 뜹니다. 이관 전에 뜬 SQLite 백업은 PG 배포로 복원할 수 없습니다(복원 CLI 가 사유와 함께 거부 — 「복구 › 1-1 복원 절차」).

주의 서버(server·edge)가 떠 있으면 pg-migrate 는 「서버가 기동 중입니다」로 멈춥니다. .env 의 메타DB 가 PostgreSQL 이 아니고 --pg 도 없으면 실행하지 않습니다. 대상 스키마에 이미 테이블이 있으면 점검에서 막히며, 그 스키마를 지우고 진행하는 --force-drop-schema 는 대상이 버려도 되는 DB 임을 확인했을 때만 씁니다.

2-3 HA 노드 순서 — 전 노드 정지 업그레이드 ​

경고 무중단 롤링 업그레이드는 지원하지 않습니다. 마이그레이션은 앞으로만 적용되므로, 먼저 기동한 신버전 노드가 스키마를 바꾸면 아직 실행 중인 구버전 노드가 맞지 않는 스키마 위에서 동작하게 됩니다. 이렇게 두 버전이 섞인 상태는 검증하지 않았습니다.

업그레이드 자동화 스크립트도 단일 호스트의 compose 만 정지·교체·기동합니다. 다중 노드를 조율하지 않습니다.

절차

  1. 공지하고 다운타임 창을 확보합니다(무중단이 아닙니다).
  2. 전 노드를 정지합니다. 일부만 멈추면 안 됩니다 — 멈추지 않은 노드가 구버전 코드로 새 스키마 위를 돕니다.
  3. 백업 2갈래를 같은 정지 창에서 뜹니다 — ① 전 노드가 멈춘 상태에서 한 노드(가능하면 직전 extract 리더)에서 ./gaea.sh backup(PG 메타DB 도 내장 정지 백업이 pg_dump -Fc 로 받습니다 — 외부 PG 는 GAEA_PG_URL 로 붙습니다. 래퍼는 자기 노드의 server·edge 만 확인하므로 다른 노드가 멈췄는지는 운영자가 봅니다) ② GAEA_SNAPSHOT_DIR 공유 볼륨 + 나머지 노드의 DuckDB 볼륨 파일 백업 — 내장 백업 아카이브에는 공유 볼륨이 담기지 않습니다.
  4. 한 노드를 먼저 올립니다. 이 노드의 부팅이 마이그레이션을 적용합니다. /api/health 의 버전과 /api/ready 200 을 확인한 뒤 다음으로 갑니다.
  5. 나머지 노드를 기동합니다. 노드마다 /api/ready 200 과 ha_leases 에 리더가 자리 잡았는지 확인합니다.
  6. 스모크 — 로그인 1회(A노드) → 다른 노드에서 GET /api/auth/me 200 + 대표 엔드포인트 조회 1건.
  7. 실패하면 롤백합니다 — 전 노드 정지 후 이전 이미지 + 3번 백업 2갈래를 함께 되돌립니다.

2-4 웹 콘솔로 업그레이드 ​

터미널 대신 브라우저에서 같은 일을 합니다. 화면이 스크립트를 대신하지는 않으며, 9단계 스크립트를 그대로 호출하고 로그를 실시간으로 보여 줍니다.

그림 2-1 웹 업그레이드 화면(airgap·sqlite 정상 경로). 사전 점검 카드가 8행(docker · docker compose v2 · 번들 버전 · 체크섬 목록 · 업그레이드 스크립트 · 이미지 반입 방식 · 메타DB 백엔드 · 디스크 여유)을 보여 주고, 9단계 표가 각 단계의 「되돌릴 수 있는가」를 배지로 표시합니다. 실행 옵션 위에는 docker image prune 금지 배너가 항상 표시됩니다.

차단 분기 — 화면이 정지 이전에 멈추는 지점 ​

스크립트와 같은 지점입니다. 화면이 새로 판정하지 않습니다.

표 2-4 웹 업그레이드 분기 — PG 는 진행, 롤백 이미지 없음·HA 는 정지 전 차단

조건화면 동작
PG 백엔드막지 않습니다. 사전 점검의 「메타DB 백엔드」 줄이 경고로 PG 자동 경로임을 알립니다. 실행하면 스크립트에 --yes 를 넘깁니다(화면의 실행 클릭이 확인을 대신합니다). PG 관련 판정은 스크립트가 정지 전에 합니다
connected 롤백 이미지 없음사전 점검 카드에 경고로 표시합니다. 스크립트가 정지 전에 확인해 서버를 멈추지 않은 채 중단합니다
HA(GAEA_HA=on)실행 버튼을 잠급니다. 배너 문구는 「다중 노드 HA 는 웹 업그레이드로 완주할 수 없습니다 — manuals/GS-DOC-04 §2-3 수동 절차」입니다(스크립트도 정지 전에 중단)

그림 2-2 웹 업그레이드 화면이 실행을 차단한 예(connected 프로파일 + PostgreSQL 메타DB + 다중 노드 HA). 사전 점검이 「롤백 이미지」·「메타DB 백엔드」를 경고로, 「다중 노드 HA」를 실패로 표시하고 실행 버튼이 잠깁니다. PG 는 경고만 남기고 진행할 수 있으며 잠금 사유는 HA 하나입니다. 배너 문구는 표 2-4.
