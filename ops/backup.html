백업 ​

백업 3수단과 권장 주기, 온라인·정지 백업, 암호화, 리허설.

1. 백업 수단 고르기 ​

온라인 백업 · 정지 백업 CLI · 파일시스템 스냅샷은 대체재가 아니라 역할 분담입니다. 어느 것을 언제 쓰는지부터 정합니다.

1-1 백업 3수단 — 언제 무엇을 쓰나 ​

세 수단은 서로를 대체하지 않고 역할이 나뉩니다. 온라인 백업은 서버가 떠 있어야 하므로 업그레이드 직전의 정지 백업을 대신할 수 없습니다. 정지 백업은 다운타임이 필요하므로 정기 백업에는 쓰지 않습니다.

표 1-1 백업 수단 비교

수단서버 상태용도정합 수준
온라인 백업(어드민 콘솔 내장)기동 중라이브 정기 백업(주 수단)메타DB·DuckDB 상호 정합 보장(적재 일시 정지)
정지 백업 CLI(이미지 내장)정지업그레이드 직전 전용정지 상태라 파일 복사가 이미 안전
FS 스냅샷(LVM/ZFS)기동 중볼륨 단위 재해복구전원 차단 직후와 같은 상태(crash-consistent)

참고 배포 형태가 single-pg(메타DB 를 PostgreSQL 에 두는 형태)여도 표 1-1 의 세 수단을 모두 쓸 수 있습니다. 온라인 백업과 정지 백업은 메타DB 를 pg_dump 로 뜨고, 나머지 절차(정합 유지·검증·암호화·보존)는 SQLite 와 같습니다(「백업 › 2-1 온라인 백업」). 단, 서버 이미지의 PostgreSQL 클라이언트가 있어야 하며, 조건이 맞지 않으면 제품은 사유 메시지와 함께 백업을 거부합니다. SQLite 로 운영하던 설치를 PostgreSQL 로 이관할 때(./gaea.sh pg-migrate — 「업그레이드 › 2-2 PG 백엔드 분기」)는 이관 전에 정지 백업을 뜨고, 이관 직후 PG 백업을 새로 뜹니다. 이관 전의 SQLite 백업은 PG 배포로 복원할 수 없습니다.

1-2 권장 주기와 보관 위치 ​

권장 주기

  • 온라인 백업 — 기본 일 1회 (어드민 콘솔에서 상향할 수 있습니다)
  • 정지 백업 — 업그레이드마다 (업그레이드 9단계의 ⑤ 단계)
  • 백업 리허설 — 분기 1회 (「백업 › 2-4 백업 리허설」 · 「복구 › 1-4 RTO 리허설」)

RPO 는 백업 주기로 정합니다. 기본은 일 1회이고 상향할 수 있습니다.

보관 위치 ​

항목내용
기본 경로<GAEA_DB 디렉터리>/backups — 온라인 백업과 정지 백업이 함께 씁니다.
바꾸는 법.env 의 GAEA_BACKUP_DIR 에 절대경로를 씁니다.
★ 이 경로는 컨테이너 안입니다기본값(/data/backups)은 도커 볼륨 gaea-onprem_gaea-data 안에 있어 호스트의 파일 탐색기나 ls 로는 보이지 않습니다. 오프사이트 복제·복구 리허설·복원 CLI 는 모두 호스트 경로를 받으므로, 먼저 볼륨에서 꺼내야 합니다(「복구 › 1-4 RTO 리허설」).

온라인 백업을 호스트로 꺼내기

  1. 백업 이름을 확인합니다(어드민 콘솔 「백업」 카드 또는 API).

    sh
    ./gaea.sh compose exec server ls -1 /data/backups

  2. 번들 디렉터리로 복사합니다. 파일 소유자가 바뀌므로 컨테이너 사용자(uid 1000)가 읽도록 맞춰 둡니다.

    sh
    mkdir -p ./backups
./gaea.sh compose cp server:/data/backups/<백업이름> ./backups/<백업이름>
chown -R 1000:1000 ./backups   # 안 하면 복구 리허설이 EACCES 로 멈춥니다

주의 기본값은 원본과 같은 디스크입니다. 운영에서는 외부 볼륨·원격 마운트를 지정하거나, 생성된 디렉터리를 오프사이트로 복제합니다.

2. 백업 실행 ​

온라인 백업은 어드민 콘솔에서, 정지 백업은 이미지 내장 CLI 로 합니다. 암호화는 선택이며, 켜면 두 경로 모두에 적용됩니다.

2-1 온라인 백업 ​

운영 중에 메타DB 와 DuckDB(적재 원본)를 서로 맞는 시점으로 함께 백업합니다. 메타DB 가 SQLite 면 온라인 백업 API 로 gaea.db 를, PostgreSQL 이면 pg_dump --format=custom 으로 gaea-meta.dump 를 뜹니다. 나머지 절차(정합 유지·검증·암호화·manifest·보존)는 같습니다. PG 는 서버 이미지의 postgresql-client-16 과 PG 서버의 메이저 버전이 같아야 하며, 맞지 않으면 「백업」 카드가 실행 전에 사유를 표시합니다.

서버가 수행하는 시퀀스

  1. 적재 대기열을 일시 중지합니다.
  2. 실행 중인 적재가 끝나기를 기다립니다.
  3. 메타DB 를 뜹니다. SQLite 는 온라인 백업 API 로, PostgreSQL 은 pg_dump -Fc 로 뜹니다.
  4. DuckDB 를 COPY FROM DATABASE 로 단일 트랜잭션에 복사합니다.
  5. 적재 대기열을 재개합니다.
  6. 백업본을 다시 열어 검증합니다.
  7. manifest.json 을 씁니다.
  8. 보존 정책에 따라 오래된 세대를 정리합니다.

참고 조회·대시보드·공유는 백업 중에도 정상으로 동작합니다. 적재만 잠깐 미뤄집니다.

주의 다중 노드 HA — 정합 창을 열 권한이 적재(extract) 리더 노드에만 있습니다. 다른 노드에서 「지금 백업」을 누르면 「다른 노드가 적재(extract) 리더입니다 — 이번 백업을 건너뜁니다」로 실패하고 부분 산출물을 남기지 않습니다. 자동 백업도 그 회차를 건너뛸 수 있으니 백업 이력에서 실제로 쌓이는지 확인합니다. 리더 노드는 ha_leases 의 resource='extract' 행 node_id 입니다. 아카이브에는 그 노드의 DuckDB 만 담기고 공유 저장소 GAEA_SNAPSHOT_DIR 는 담기지 않습니다 — 공유 저장소는 파일 백업으로 따로 뜹니다.

실행 ​

항목내용
화면어드민 콘솔 → 「시스템 관리자」 탭 → 「백업」 카드 → 지금 백업
APIPOST /api/admin/backup — 202 로 받고, 동시 1건만 돕니다.

자동 백업 설정 ​

같은 카드의 「자동 백업 설정」에서 다섯 가지를 편집합니다.

  • 자동 주기
  • 저장 경로
  • 보존 세대 수
  • 보존 총 용량 상한(GB)
  • 정지 대기 상한(초)

주기 변경은 서버를 재시작하지 않아도 다음 주기부터 반영됩니다.

표 2-1 온라인 백업 산출물

산출물내용
gaea-backup-<ISO8601>/gaea.dbSQLite 메타(better-sqlite3 온라인 백업 API)
.../gaea-meta.dumpPostgreSQL 메타(pg_dump --format=custom — gaea.db 대신. 검증은 pg_restore --list)
.../gaea.duckdbDuckDB 적재 원본(COPY FROM DATABASE, 별도 로그 파일 없이 단독으로 복원 가능)
.../manifest.json시각 · 소요 · 파일 크기 · sha256 · 마이그레이션 헤드 · 검증 결과
.../gaea.db-wal, .../gaea.db-shmSQLite 부속 파일. 함께 만들어집니다(manifest.json 의 files 목록과 sha256 검증 대상은 gaea.db·gaea.duckdb 둘뿐입니다). 백업을 옮길 때는 디렉터리째 옮깁니다.

2-2 정지 백업 CLI ​

업그레이드 직전·이설처럼 서버를 내려야 하는 상황, 또는 제품이 뜨지 않아 어드민 콘솔에 들어갈 수 없을 때의 수단입니다.

CLI 는 런타임 이미지 안(dist/scripts/backup.js)에 있고, ./gaea.sh backup 이 오버레이(jdbc·pg·ha)와 이미지 태그를 맞춰 대신 불러 줍니다. 번들만 있는 폐쇄망 호스트에서도 저장소 체크아웃 없이 동작합니다.

절차

  1. 서버를 정지합니다 — 정지 상태가 전제입니다(server·edge 가 떠 있으면 래퍼가 거절합니다).

    sh
    ./gaea.sh stop

  2. 정지 백업을 뜹니다.

    sh
    ./gaea.sh backup                       # 기본 ./backups — 다른 곳: --dir <디렉터리>
# → ./backups/gaea-backup-<타임스탬프>.tar.gz[.enc]  (권한 0600)

  3. ./system/restore-rehearsal.sh <아카이브> 로 실제 복원 시간을 재 둡니다(「백업 › 2-4 백업 리허설」).

항목내용
PostgreSQL 메타DB지원합니다. 번들 PG 면 래퍼가 meta-postgres 만 healthy 까지 올린 뒤 pg_dump -Fc 로 뜹니다(그 컨테이너는 「기동 중」으로 세지 않습니다). 외부 PG 는 .env 의 GAEA_PG_URL 로 붙습니다
권한새로 만드는 백업 디렉터리는 0700, 아카이브는 0600 이고 실행한 계정이 소유합니다. 같은 호스트의 다른 계정은 읽을 수 없습니다
다중 노드전 노드를 멈춘 뒤 한 노드에서 돌립니다. 래퍼는 자기 노드의 server·edge 만 확인합니다. 공유 저장소는 담기지 않으므로 같은 창에서 따로 백업합니다
실패하면원본 DB 는 건드리지 않습니다. Permission denied 면 /data 소유·권한 문제입니다

참고 웹 운영 콘솔의 「정지 백업」 카드도 같은 명령을 실행합니다. 래퍼 없이 docker compose run(1.3.0 번들 루트에서는 ./gaea.sh compose run)으로 직접 실행할 때는 래퍼와 같은 조건(--user 0 · /data 읽기 전용 사본 · *.duckdb.wal 포함 · --cap-add DAC_OVERRIDE)을 그대로 지킵니다.

2-3 백업 암호화 ​

항목내용
켜는 법.env 에 GAEA_BACKUP_ENC_KEY 를 설정합니다. 설치 마법사는 값이 비어 있으면 새로 만들어 넣습니다(--no-backup-enc-key 로 끔 — 이미 있는 키는 지우지 않음). 업그레이드 스크립트는 키를 만들지 않으므로, 기존 설치본은 마법사를 다시 실행하기 전까지 그대로입니다.
키 형식32바이트 base64 또는 64자 hex
적용 범위온라인 백업과 정지 백업 CLI 양쪽. 산출물을 AES-256-GCM 스트리밍 암호화합니다(.enc).
미설정이면평문 그대로입니다(기능은 정상). 키가 생긴 뒤의 백업부터 .enc 이고, 그 전의 평문 백업도 그대로 복원됩니다.

키 교체 ​

절차

  1. GAEA_BACKUP_ENC_KEY_PREVIOUS 에 이전 키를 넣습니다.
  2. GAEA_BACKUP_ENC_KEY 를 새 키로 바꿉니다.

이전 키와 새 키로 만든 백업 모두 키 지문(fingerprint)으로 맞는 키를 자동으로 골라 복원할 수 있습니다.

참고 키 원문은 로그·오류 메시지·manifest 어디에도 남지 않습니다. 남는 것은 8바이트 지문(fingerprint)뿐입니다.

키는 백업 매체에 들어 있지 않습니다 ​

표 2-2 분실하면 되살릴 수 없는 키 2종

키분실하면
GAEA_BACKUP_ENC_KEY암호화 백업을 되살릴 방법이 없습니다.
GAEA_DATASOURCE_CONFIG_KEY데이터소스 자격증명·2FA 를 전량 재등록해야 합니다.

경고 두 키는 백업 매체에 들어 있지 않습니다. 반드시 백업과 다른 매체에 최소 2곳 이중 보관합니다(「복구 › 2-1 사전 준비물」 사전 준비물).

보관본 만들기 — 키 복구 시트 ​

sh
./gaea.sh keys export                 # → gaea-recovery-keys-<호스트>-<시각>.txt (0600)
./gaea.sh keys export --encrypt       # 12자 이상 암호로 잠근 .enc

위 두 키 + 번들 PG 비밀번호 + SSO 서명키의 값과 지문(SHA-256 앞 16자)을 담습니다. 화면에는 지문만 찍힙니다. 지문은 백업 .enc 헤더의 키 지문(8바이트, 16진수 16자)과 같은 규칙이라, 「이 백업을 어느 키로 풀어야 하는가」를 값 없이 대조할 수 있습니다. 파일을 서버 밖으로 옮기고 서버에서는 shred -u 로 지웁니다. 마법사가 키를 새로 만들었으면 설치 끝에 자동으로 만들어 경로를 알려 줍니다.

주의 다중 노드는 백업 암호화 키도 전 노드가 같아야 합니다 — 리더가 바뀌면 다른 노드가 백업을 만듭니다. 추가 노드는 1번 노드의 합류 꾸러미(./setup.sh --export-join → --join)로 설치해 키를 그대로 받습니다(「설치」).

2-4 백업 리허설 ​

system/restore-rehearsal.sh(번들 루트에서 ./system/restore-rehearsal.sh)는 운영 데이터와 운영 인스턴스를 건드리지 않습니다. 별도 임시 볼륨·포트에서 실제로 복원해 복구 시간(RTO)을 측정합니다.

항목내용
권장 주기분기 1회
상세 절차「복구 › 1-4 RTO 리허설」 RTO 리허설에 명령과 측정 기준값이 있습니다.
실패하면「일상 운영 › 3-2 흔한 증상과 조치」로 갑니다.

참고 복원해 보지 않은 백업은 장애 때 실제로 복원된다는 보장이 없습니다.
