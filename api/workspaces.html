GET /api/workspaces/:id/inventory ​

로그인 세션 · 개인 액세스 토큰 · 임베딩 키

BI Builder 「인벤토리」

자세히

BI Builder 「인벤토리」 — 워크스페이스 전역의 아이템(저장 보기) 목록(설계 SoT docs/roadmap/38-bi-builder-inventory.md). 쿼리 q(이름 부분일치) · kind(table|chart|pivot|kpi|cohort) · datasourceId · projectId · siteId · registered=1(v2 — 인벤토리에 등록된 보기만 = saved_views.inventory_json IS NOT NULL) · include=pages[,widgets](v2 — 3종 서랍) · cursor · limit(1~200, 기본 50). 응답 { items: BiInventoryItem[], pages?: BiInventoryPageEntry[], widgets?: BiInventoryWidgetEntry[], nextCursor?, truncated? } — 각 항목에 조합기 CP-4·CP-5 파생 필드 2종(studioVisible: boolean — 늘 실림, 배치가 kind<>'site' 프로젝트인가 · placementMovable?: boolean — ?siteId= 를 준 호출에서만, PATCH …/views/:viewId/placement 와 같은 함수 isViewPlacementMovable 로 스위치를 노출해도 되는 보기인지) + 서버가 파생한 kind(@gaea/types primaryPaneKind, 클라이언트 viewModeToKind 와 같은 규칙) · projectId/projectName · endpointId/endpointName · datasourceName · usageCount(배치 수 = 역참조) · fieldCount?/conditionCount?(INVCOUNT — 종류별로 다르게 파생: table 은 endpoints.col_count − 숨긴 컬럼, pivot·chart 는 rows∪cols∪values[].field, cohort 는 cohortDateField·entityField; conditionCount 는 저장 보기 필터 배지와 같은 규칙. 종류를 모르거나 설정이 비면 생략 — 0 과 「모름」을 섞지 않아요)를 실어요(N+1 없음 — 페이지당 목록 1문 + 사용처 집계 1문, fieldCount/conditionCount 는 이미 조회한 config·col_count 에서 TS 로만 파생해 추가 쿼리 0). 공개범위는 공용 술어 db/view-visibility.ts(workspace 공개 전부 + 내 private), 프로젝트는 공용 술어 db/project-kind.ts(사이트 전용 프로젝트 제외). siteId(선택) 를 주면 그 사이트의 자기 페이지 프로젝트 하나만 더 보여요(visibleProjectsSqlForSite — 40 S7 의 두 번째 호출자). BI 빌더가 「＋ 새 아이템 만들기」로 그 프로젝트에 저장한 아이템을 목록에 되돌리기 위한 것이고, 다른 워크스페이스·소프트 삭제된 사이트·없는 id 는 아무것도 넓히지 않으며 siteId 없는 호출은 종전과 동일해요. usageCount 도 걸러낸 집합에서만 세요(파생 메타 간접 유출). 잘못된 커서 400 invalid_cursor · 잘못된 쿼리 400 invalid_query. v2 — ① include 로 켠 것만 더 실어요(안 켜면 응답 키가 늘지 않아요): pages = 대시보드(프로젝트) 통째(pageCount·widgetCount·data[]·usageCount = 이 대시보드를 페이지로 쓰는 사이트 수), widgets = 대시보드의 배치 각각(savedViewId·kind·conditions[]·usageCount = 같은 보기를 놓은 배치 수 · filters(원본 자리 조건 WidgetFilterConfig \| null)·drillthrough(DrillthroughConfig \| null) — 위젯형 배치 때 새 자리가 물려받는 원본). ② 3종에는 커서가 없다 — include 와 cursor 를 함께 주면 400 invalid_query(서랍을 열 때 첫 호출 1회만 include). ③ 3종이 서버 방어 상한에서 잘리면 truncated: true. ④ items[].usageCount 는 배치 수 + 이 보기를 분석형 페이지로 쓰는 사이트 수이고, 등록된 보기에는 registered(등록 표지 { registeredAt, registeredBy, label?, note? })·conditions·shelfLock 이 해당될 때만 붙어요. ⑤ 리소스 한정 PAT 에는 사이트 사용처를 한 건도 더하지 않는다(fail-closed — 사이트는 PAT 스코프가 모델링하는 리소스가 아니라 거를 축이 없어요). q·limit·cursor 는 items 에만 걸려요
